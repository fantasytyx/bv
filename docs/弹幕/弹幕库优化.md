## 变更总结

### DanmakuItem.kt
新增 `isActive` 标志位，用于标记弹幕是否处于活跃状态，避免通过遍历 active 列表来判断。

### DanmakuEngine.kt — 三大改动方向：

**1. 移除 pending 重试机制**
- 删除了 `PendingSpawn` 数据类和 `pending: ArrayDeque` 队列
- 删除了每帧重试 pending 弹幕的逻辑和相关常量（`DELAY_STEP_MS`、`MAX_DELAY_MS`、`MAX_PENDING`、`MAX_PENDING_RETRY_PER_FRAME`）
- 现在放不下轨道的弹幕直接丢弃，不再排队重试

**2. 轨道状态管理重构**
- **滚动弹幕**：从每帧 `Arrays.fill` 重建 `laneLastScroll`/`laneLastScrollTail` → 改为持久化的 `scrollLaneQueues: Array<ArrayDeque<DanmakuItem>>`，只做增量清理（`cleanupScrollLaneQueue`），用 `isActive` 标记判断是否过期
- **固定弹幕**：从存储 `laneLastTop`/`laneLastBottom`（引用对象后每帧扫描比较时间）→ 改为 `topLaneBusyUntilMs`/`bottomLaneBusyUntilMs`（`DoubleArray`），直接比较数值，无需引用对象

**3. 快照发布 & 缓存构建优化**
- 引入 `snapshotDirty` 脏标志，只在 active 列表变化时才重建快照（`publishSnapshotIfDirty`），而非每帧都重建
- 快照不再存储 `x` 坐标，改为 `draw()` 时实时计算 `scrollX`，减少快照写入量
- 缓存构建从每帧全量扫描 active → 改为 `cacheProbeCursor` 轮询探测，每帧最多扫描 `MAX_CACHE_SCAN_PER_FRAME=16` 项

---

**性能提升主要体现在：**

| 优化点 | 效果 |
|---|---|
| 移除 pending 队列 | 消除每帧重试开销和内存压力，弹幕高峰期（如高能进度条处）不再因 260 条 pending 反复重试拖慢 action 线程 |
| 轨道状态增量维护 | 旧实现每帧对所有轨道 `Arrays.fill` + 遍历全部 active 重建轨道映射，$O(active)$；新实现只做队列头尾的过期清理，通常为 $O(1)$ |
| 固定弹幕轨道用 `DoubleArray` | 减少对象引用和比较开销，CPU cache 更友好 |
| `snapshotDirty` 脏标志 | 无新增/移除弹幕的帧跳过整个快照构建，减少对象拷贝和数组操作 |
| 缓存构建轮询探测 | 从每帧 $O(active)$ 全量扫描降为最多 16 项，弹幕密集时显著降低每帧耗时 |
| draw 时实时算 x | 快照写入少一个 float 数组，减少 action→UI 线程的数据传输量 |

**潜在取舍**：放弃 pending 意味着轨道满时弹幕会被直接丢弃，弹幕密集场景下显示数量可能略少，但换来了更稳定的帧率。整体来看是合理的性能优化。



# Plan: DanmakuView 绘制路径优化

消除不必要的硬件层开销 + 缓存预热消除 drawTextDirect fallback。不涉及架构重构，改动集中在 DanmakuView 和 DanmakuEngine。

## Steps

### Phase 1: 消除无条件 LAYER_TYPE_HARDWARE（主要优化）

1. **问题**：DanmakuView.kt L27 `init { setLayerType(LAYER_TYPE_HARDWARE, null) }` — 始终开启硬件层。硬件层的设计目的是给**静态内容 + 变换动画**用的（比如 alpha/translate 动画）。弹幕内容每帧都变（invalidate），硬件层反而**每帧要重新渲染整个层纹理再合成**，比 `LAYER_TYPE_NONE`（直接绘制到 display list）多一次完整的纹理拷贝。

2. **修改**：只在有蒙版时使用硬件层（DstIn 混合需要离屏 buffer），无蒙版时用 `LAYER_TYPE_NONE`。在 `onDraw()` 中根据 `maskFrame` 是否为 null 动态切换。
